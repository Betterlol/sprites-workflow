# 本地 Sprite 动作工作台

## 启动

Python 3.10+，在仓库根目录运行：

```powershell
python -m pip install -r tools/requirements-workbench.txt
python tools/serve_sprites.py
```

默认打开 `http://127.0.0.1:8765` 的工程列表，服务仅监听本机。支持新建、打开和切换 `workspaces/` 下的工程；可用 `--workspace-root` 指定工作区根目录、`--config` 直接打开已有工程（包括旧布局）、`--port` 指定端口、`--no-browser` 禁止自动打开浏览器。关闭服务终端即可停止。

新建工程时设置名称、目录名、画布大小和归一化锚点。目录名留空则使用名称，支持中文。新工程可以没有原图和动作，也可以仅导入 processed 单帧。工作台不会自动迁移 `assets/`。目录和 CLI 约定见 [工作区说明](../workspaces/README.md)。

打开工程后可在“工程设置”修改展示名称、画布尺寸和锚点。这些修改先进入可撤销草稿；保存工程只写参数，不自动缩放或覆盖已处理图片。改变画布或锚点后，原图处理结果会标记待更新，需要逐张重新应用。`imports/` 和 `_approved/` 的手工素材不会自动改变；画布尺寸变化时应按新画布重新制作或导入，之后再导出资源。

首次打开会读取现有 processed 和动作。没有 processed 时，可以“准备缺失素材”，只生成尚未存在的原图处理目录。已有目录不会被这个操作重建。

## 编辑与保存

工程仍为 version 2 的 `pipeline.json`，既有字段、额外元数据和路径映射会保留。Review 是额外的 `workbench.reviews` 字段，CLI 会忽略它。

| 操作 | 配置 | processed | 其他输出目录 |
| --- | --- | --- | --- |
| 参数预览、动作播放、时间轴编辑 | 仅网页草稿 | 不变 | 不变 |
| 保存工程 / Ctrl+S | 保存当前草稿 | 不变 | 不变 |
| 应用处理并保存工程 | 保存整个草稿 | 更新所选原图 | 不变 |
| 准备缺失素材 | 保存整个草稿 | 仅补充缺失原图 | 不变 |
| 导入图片 / 保留已有最终帧 | 保存整个草稿 | 添加素材 | 不变 |
| 导出 | 不变 | 只读 | 临时生成 ZIP 下载 |

更改处理参数后，动作预览仍使用已经应用的 processed 图片。参数预览并未提交为素材；确认后点击“应用处理”。仅保存规则不会自动重算图片。已由工作台处理的原图会在规则或源图改变后显示“待更新”。

编辑操作支持撤销 / 重做，草稿历史保留在本次网页会话中。应用、准备、导入、迁移和删除会另存受影响文件的上一版本；点击“版本记录”可恢复。恢复前会检查当前配置、素材版本和相关文件，拒绝覆盖操作之后的外部修改。恢复本身也留下可再次恢复的版本。版本保存在工程的 `.sprite-workbench-history/`，不随普通资源导出或完整工程 ZIP 携带，使用时间久后会占用磁盘空间。旧布局若将待修改文件放在工程目录外，应先手动导出完整工程备份。关闭网页前仍会提醒未保存草稿。

CLI 使用 `python tools/projects.py history <工程 ID>` 查看版本，再用 `python tools/projects.py restore <工程 ID> <版本 ID>` 恢复；可附上 `--revision` 和 `--asset-revision`，按先前读取的版本号拒绝过期提交。

保存使用工程文件摘要做冲突检查。其他窗口或 CLI 改变配置后，旧窗口不能直接覆盖它；有未保存草稿时可点击“合并配置”。网页会自动合并双方修改的不同字段，双方都修改的字段逐项选择当前草稿或磁盘版本。动作帧数组作为一个字段处理，不按位置悄悄拼接。合并结果仍是未保存草稿，检查后再保存；若此时磁盘又变化，保存仍会被拒绝。也可下载配置草稿后自行合并。

工作台在页面可见时每 12 秒、以及返回窗口时检查外部修改。没有未保存编辑时自动更新；有草稿时显示提示并保留草稿。仅图片变化可点击“刷新”更新素材而保留配置；配置也变化时，可先“下载配置草稿”，再重新载入并合并。切换工程会提醒未保存修改。

网页、`projects.py` 和分阶段 CLI 共用工程级跨进程锁。素材写入同时检查素材版本，避免旧页面覆盖 Agent 更新的图片。手工直接写文件不受锁控制，建议先写临时文件再替换，并让网页刷新后再继续处理。

## 素材处理

1. 点击“素材处理”，选择原图；左上角 ＋ 可导入原图。
2. 选择自动连通域、规则网格、手动区域或整张单帧。连通域适合透明角色图，网格适合严格排布的图集。
3. 在“原图 / 切图”中拖出矩形可切换到手动框选。切图区域及高级参数也可通过 JSON 调整。连通域还会将分离的小特效归属到邻近主体；框选则保留矩形内的完整像素。
4. 调整整组缩放、目标高度、位置、画布内限制和越界策略。`fit_height` 按整组最高轮廓计算共享倍率，不把每一帧拉成同样高度。
5. 时间轴选择某帧，设置该帧的偏移或绝对缩放覆盖。清空“目标高度”可停用自动高度适配；单帧缩放留空则继承整组倍率。
6. 检查结果后应用。共享该素材的所有动作随之更新。

项目使用 `pipeline.json` 中统一的 `frame_size` 和 `anchor`。工作台显示固定地面线与锚点，不逐帧自动调整显示大小。导入 processed 单帧需与工程画布一致。

素材编号按区域匹配保留：相同框优先，其次是不歧义的高重叠区域。新区域分配新的编号。应用后将 ID 与原图区域的对应关系保存在 `extract.identities` 中，因此清理切图缓存、重开工程或用 CLI 重建时也可恢复相同 ID。自动匹配不能替代人工确认；切图发生较大变化时，应检查每帧身份。若仍有动作引用被移除区域，会阻止应用，请先调整引用。切图删除的帧若仍有处理覆盖，也需在“处理规则 JSON”中移除相应覆盖。

## 动作编排

原图、processed 和参考图的文件选择器均支持多选。图片逐张提交，界面显示进度；某张图片无效或重名时会报告失败并继续处理其他图片，已成功导入的图片会保留。发生版本冲突或会话失效时停止队列，提示剩余未处理数量。每张图片最大 40 MiB。

素材库勾选“多选”，或直接 Ctrl / Shift 点击素材，可选择多张；Shift 支持按当前筛选顺序连选。“全选当前结果”只选择搜索和来源筛选后的素材，“清空”清除选择。“加入动作”按素材库顺序批量添加，作为一次可撤销操作，游戏播放模式下可用。

“删除”会删除已选择的 processed 文件；原图列表上方的“删除原图”同时清理对应切片缓存、processed 和该原图规则。删除会保存当前草稿，不能通过网页撤销。若任一待删素材仍被动作使用，整批删除会被阻止并列出动作名称；请先移除或替换引用。删除自动生成的单帧不改变原图切图规则，以后重新应用原图可能再次生成它。文件或配置写入失败时，删除操作会恢复此前移走的文件和元数据。

- 点击 ＋ 创建动作，ID 使用字母、数字、下划线或短横线。
- 点击素材或拖入时间轴，支持跨原图取帧及多次使用同一张素材。
- 拖拽排序，支持重复、倒序、删除。动作只存引用，实际 PNG 不会复制一份。
- “游戏播放”按素材顺序和动作 FPS 播放；图集和元数据使用此顺序。
- “展示播放”支持独立排序、重复、逐步停留时长，以及 WebP 循环次数。0 次表示无限循环。
- 调整游戏帧槽位时，会保留已有展示顺序与时长的对应关系；可用“恢复为游戏播放”清空展示覆盖。
- “定位到素材处理”可回到原图处理页。独立导入或已确认素材没有可自动重建的原图对应关系。

播放 / 暂停为 Space，左右方向键单步，Delete 删除选中游戏帧，Ctrl+Z / Ctrl+Shift+Z 撤销 / 重做。预览循环和播放倍速仅影响当前查看，不改写游戏或 WebP 参数。

## 衔接 Review

可保存多个序列，每个片段设置动作、重复次数、起始步和结束步（0 起，结束包含在内，空值表示播放到末尾）。Review 可选择游戏或展示播放参数。

例如 `idle × 2 → attack × 1 → idle × 2`、`jump → land → idle`。首次打开大肥鱼工程会生成这两个建议序列作为未保存草稿，保存后才写入配置。

点击片段，再使用“衔接前一帧”和“片段第一帧”，配合前帧叠图、Idle 参考、固定画布、慢放，检查大小及姿势变化。此处直接切帧，不添加会掩盖问题的插值或淡化。

每个片段最多重复 100 次，一个序列最多 10,000 步。缩短动作后，网页会把现有 Review 的越界范围限制在新的有效范围内。Review 导出包含 WebP 及逐步来源和时长记录，即使编码器合并相同连续画面，也可追溯原始编排。

## 参考图

“参考图”页签支持批量导入、原尺寸查看和删除参考图片。新图片保存于工程的 `references/`，不加入 source 扫描、processed 素材库或动作。已有 `reference/` 中的图片也可查看和删除，原目录不自动迁移。完整工程备份会同时保留两种目录中的资料，包括图片以外的说明和提示词。

## 迁移手工最终帧

在开始重新编排前，点击“保留已有最终帧”：

1. 读取现有最终帧的编号顺序。
2. 与动作中相应位置引用的 processed 比较像素。
3. 不同或缺失的帧复制到 `processed_sprites/_approved/<action>/`。
4. 按已有最终帧重新建立该动作的素材引用，并保存。

这个操作保留了人工修图，但也会以已有最终帧为准恢复该动作的顺序和帧数，因此应在开始新编排前使用。原来的 `frames/` 不删除、不覆盖。若历史最终帧和当前展示 / Review 范围不兼容，会报错并保留旧工程，请先调整配置。

## 导出与备份

- **PNG 帧序列**：按游戏顺序编号的单帧 ZIP。
- **图集**：PNG、TexturePacker Hash JSON、动作元数据和 manifest。
- **WebP**：按展示顺序、逐步时长和展示循环编码，并附播放记录。
- **完整动作资源**：包含上述三类，可选择一个或多个动作。
- **Review**：当前 Review 的 WebP 与播放记录。
- **完整工程**：原图、processed PNG / 阶段描述、工程 JSON、`references/`（及已有 `reference/`）和工程 `README.md`。路径统一为相对路径，解压到 `workspaces/<目录名>/` 即可在列表中打开，也可以通过 `--config` 打开。切图缓存和交付目录不包含在备份中。

其他导出类型用于交付游戏资源；需要重新打开整个编辑工程时，请选择“完整工程”。所有导出都基于当前动作草稿和已应用的图片，不要求先保存配置，也不写入项目的 `frames/`、`sheets/` 或 `previews/`。

`source_sprites/`、临时文件、锁和工作区工程的 `exports/` 被 Git 忽略。processed 全部默认保留，其中 `_approved/` 和 `imports/` 尤其不能按缓存清理。

## 开发与检查

前端：`tools/sprite_pipeline/web/`，原生 ES modules、Canvas 2D。
服务：`server.py` 处理 HTTP / 同源会话，`workbench.py` 处理草稿、渲染、迁移、导出。
CLI 与网页共用 `cut_frames`、`process_images` 和已有打包逻辑。

```powershell
python -m pip install httpx
python -m unittest discover -s tests -v
node tests/test_workbench_model.mjs
node tests/test_workbench_session.mjs
```

Node 仅用于可选的前端模型检查，日常运行工作台不需要 Node。
