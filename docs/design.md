# 设计理念

Sprite Workbench 将原图整理、逐帧调整和动画编排放在同一个本地工程中。网页用于交互编辑，命令行用于可重复的批量操作；两者共用配置、素材和核心规则。

## 保留原图，区分各阶段成果

原图、原始切片、正式单帧与导出文件各有用途。切割保留原始像素尺寸，处理负责统一画布和锚点，编排通过引用复用正式单帧，导出再生成目标格式。原始切片是可重建缓存，正式单帧可能包含人工修图，应作为工程成果保留。

## 编辑、预览与写入分别发生

参数编辑先进入草稿，预览在内存中计算。保存工程只提交配置；保存切割提交指定原图的切割规则和切片；应用调整才更新正式图片。准备缺失素材保留已有单帧，图像应用尽量只写入实际变化的帧。

## 用资源引用表达动画

单帧、动作与序列可以通过槽位组合，槽位描述顺序、重复、速度和时长。稳定的帧与槽位身份使调整和重排能够延续已有引用。Review 用于检查片段衔接，删除与重新切割会检查已保存的引用关系。

运行时播放与展示播放分开配置：日常调整和游戏资源遵循运行时编排，WebP 与 GIF 可使用独立的展示顺序和时长。

## 同一工程可以被多个入口安全使用

`pipeline.json` v2 集中保存规则与编排，素材以普通文件存放。工程写入使用进程锁、配置与素材版本检查；网页保留未保存草稿并处理外部修改。图片操作保留受影响文件的恢复记录，恢复前再次核对当前文件，避免覆盖后续修改。

网页与工程 CLI 的导出读取当前资源，在临时目录生成 ZIP；分阶段 CLI 则明确写入阶段输出。这两个入口服务于不同的操作需求，操作命令文档分别说明其写入范围。

## 保持实现与说明的职责清晰

规则、图像计算、存储、应用操作和界面适配分层实现。网页使用原生模块，无需构建服务。文档只维护四个入口：README 负责安装启动，结构文档负责文件职责，命令文档负责可执行操作，本页负责稳定的设计约定；参数细节由各命令的 `--help` 提供。
