# Sprite Workbench development

- Project data lives in `workspaces/<project-id>/`; read `workspaces/README.md` before operating on artwork.
- Use `tools/projects.py` for project creation, inspection, config saves, imports, processing and exports. It shares the browser's domain operations, revisions and process locks.
- Treat `pipeline.json`, source images, processed sprites and reference material as shared human/agent work. Preserve existing files and unsaved-work conflict protection.
- Keep `references/` selective: place user-provided character references there, then add one approved idle key pose as the character baseline. Generate later actions primarily from that idle pose, optionally alongside the user's original reference. Match its proportions, scale, palette and ground anchor. If the idle image is also a playable sprite, import its accepted original into `source/` as well. Do not store candidates or iteration images in `references/`; legacy `reference/` remains readable and is included in backups. References do not participate in extraction.
- Keep drafts, generated variants and other working files in an agent-owned task directory outside `references/`, `source/` and `processed_sprites/`, such as `workspaces/<project-id>/_work/<task>/`. Once artwork is selected, import the accepted original into `source/` before extraction and processing, including a single-frame correction. Keep processed results in their source-derived directories; treat `processed_sprites/imports/` and `_approved/` as existing compatibility or archival material, not the routine path for new artwork.
- Generate or extend an animation as a coherent spritesheet, including short actions and in-between motion. For a long animation, make a separate source spritesheet for each semantic subaction, keep those actions playable on their own, and build the complete action from the same processed references. Start each new subaction's sheet with the preceding action's approved last frame or an exactly matched pose; play a shared boundary frame only once unless a deliberate hold is needed. A single idle key pose may serve as a reference; an animated idle still needs a spritesheet.
- For every handoff between subactions, use the preceding action's last frame and the following action's first distinct pose as endpoint constraints for a whole transition spritesheet. Cut and review the sheet at both boundaries. Generate an isolated frame only to repair a specific faulty frame, never to assemble a transition from scattered middle frames; put any accepted repair in `source/` first.
- Review each subaction, each handoff and the complete sequence at runtime speed and frame by frame. Check character scale, ground anchor, expression and prop state; archive superseded work before removing it from the active project. Do not renumber reusable sprites to change action order.
- Use repeated `--file` for imports and repeated `--ref` for deletions; deletion rejects assets still used by actions.
- Do not migrate, regenerate, delete or reorganize the existing `assets/` unless the user explicitly asks. Tests use temporary projects and synthetic images.
- Validate changes with `python -m unittest discover -s tests -v`, `node tests/test_workbench_model.mjs` and `node tests/test_workbench_session.mjs`. Browser startup uses `python tools/serve_sprites.py`; no frontend build is required.
